# 「着席なう」システム仕様書

> プロジェクトの正本仕様。実装判断はこのファイルと [`er-diagram.md`](./er-diagram.md) を随時参照する。

## 1. システム概要

### 1.1 システム名
着席なう（仮称）

### 1.2 プロジェクトの背景
- 現在の出席確認は、教員が口頭で生徒の名前を呼び、紙の記録帳に記入後、システムへ再入力するアナログで非効率なプロセス。
- 複数クラス合同の講義では出席確認に多大な時間を要し、人的ミスも発生しやすい。
- 生徒の滞在時間の正確な把握や、登校に対するモチベーション向上の仕組みが不足している。

### 1.3 導入目的
- BLE（Bluetooth Low Energy）と Web/モバイル技術を組み合わせ、出欠確認を完全自動化・効率化する。
- 削減された時間を教員と生徒のコミュニケーション（雑談や対話）に充てる。
- 出席状況の可視化やゲーミフィケーション要素により、生徒の登校意欲を高める。

## 2. 対象ユーザーと利用範囲
- **生徒（主ユーザー）**: アプリをインストールしたスマートフォンを所持して教室にいるだけで、自動的に出席が記録される。
- **教員（管理ユーザー）**: Web アプリを通じて、リアルタイムの出席状況の確認や、自動判定結果の修正を行う。
- **対象校**: 国際理工カレッジを初期対象とし、将来的な横展開を視野に入れる。

## 3. システム構成・技術方式

### 3.1 全体構成
- フロントエンド（生徒用）: iOS/Android ネイティブアプリ。
- フロントエンド（教員用）: ブラウザで動作する Web アプリケーション。
- バックエンド: Firebase を活用したサーバーレス構成。

### 3.2 出席判定メカニズム
- **学内授業（ビーコン方式）**: 教卓機から BLE ビーコン信号を、生徒のスマホがバックグラウンドで検知し、滞在情報を送信する。
- **学外授業（GPS クラスタリング方式）**: GPS を利用し、クラスメイトの現在地データの中心点から一定半径（例: 500m）以内に存在しない「外れ値」の生徒を自動的に欠席（または離席）として判定する。
- 発信元: 教員用 PC（Web アプリまたは連携ツール）からビーコン信号を発信、あるいは教室に設置されたデバイスを活用。
- 受信判定: 生徒のスマホがバックグラウンドで信号を検知し、Firebase へ滞在情報を送信する。

## 4. 機能要件

### 4.1 出欠判定ロジック
- **出席の確定（一言コメント認証）**: 授業開始時、教員から簡単な質問（お題）が出題される。生徒がその質問に対して一言コメントを送信した時点をもって、正式な「出席」として確定する（スマホの教室放置による不正を防止）。※スキップも可。
- **滞在の継続判定**: コメント送信後、授業終了まで指定エリア（学内はビーコン検知圏内、学外は GPS の許容半径内）にいることを条件に出席状態を維持する。
- **30 分以上の離席**: 授業中に 30 分以上ビーコン信号が途切れる、または GPS の許容範囲から外れた場合は、システムが自動的に「欠席（または中抜け）」と判定。
- **自動判定の修正**: 遅刻・早退・中抜け等はシステムがフラグを立て、最終的には教員が管理画面で承認・修正を行う。
- **公欠登録**: 生徒の公欠の時間を指定すると公欠のフラグを立てることができる。

### 4.2 生徒用アプリ機能
- バックグラウンド検知: アプリを閉じていても出席を記録。
- 出席履歴表示: 自身の出席状況をカレンダー形式などで確認可能。
- 称号・育成機能（拡張）: 出席状況に応じた称号獲得やキャラクター育成要素。
- 一言コメント回答: 授業開始時の教員からの質問（お題）を受信し、回答を入力・送信する機能。

### 4.3 教員用 Web アプリ機能
- ダッシュボード: リアルタイムでのクラス出席率、現在室者のリスト表示。
- 出欠修正: システムの自動判定に対する手動上書き機能。
- CSV 出力: 既存の出席管理システムにインポート可能な形式でデータを出力。
- 生徒の登録: 生徒の名前、クラスを登録可能。
- 時間割の登録: 時間割を登録可能。
- （進級機能）: 進級すると生徒のクラスの階級を一括であげられる。
- 質問送信・コメント閲覧機能: 授業開始時に生徒へ一言質問（お題）を送信し、リアルタイムで生徒からの回答コメントを一覧表示する機能。

## 5. 技術スタック

### 5.1 モバイルアプリ（生徒用）
- iOS: SwiftUI (Native)
- Android: Kotlin (Native)
- ※バックグラウンドでの安定した BLE スキャン性能を確保するためネイティブ開発を採用。

### 5.2 Web アプリ（教員用）
- 技術選定: React または Vue.js 等のモダンなフロントエンドフレームワーク。
- 配信: Firebase Hosting。

### 5.3 バックエンド・インフラ（Firebase）
- Authentication: ユーザー認証（生徒・教員のアカウント管理）。
- Cloud Firestore: 出欠データ、ユーザープロフィール、教室情報のリアルタイム保存。
- Cloud Functions: 出欠判定ロジックの実行、定期的な集計処理。
- Cloud Messaging (FCM): 遅刻判定や通知のプッシュ配信。

## 6. 外部連携
- 既存システム連携: 抽出した CSV ファイルを学校側の既存システムにインポートすることで、教員の事務作業を最小化する。

## 7. 非機能要件

### 7.1 セキュリティ
- Firebase Authentication によるメール＋パスワード認証を採用。生徒・教員で role を分離し、Firestore セキュリティルールで権限を制御する。
- クライアント・Firebase 間の通信はすべて HTTPS/TLS で暗号化。
- Firestore に保存する個人情報（氏名・出欠履歴・位置情報）は外部に提供しない。位置情報は出席判定にのみ使用し、判定後は生の座標を保持しない。

### 7.2 パフォーマンス
- 想定同時利用者数は最大 1000 名。
- 5 分毎にビーコン信号から Firestore へ反映。

### 7.3 可用性・信頼性
- 平日 8:30〜17:00 に 95% 以上の稼働を目標とする。
- BLE・GPS 検知が失敗した場合、再度検知を行う。それでもなお検知できず、実際の出席状況と異なる場合は教員が手動で修正できるようにする。
- Firestore のデフォルトバックアップおよび Cloud Functions の冗長化により、データ損失リスクを最小化する。

### 7.4 保守性・運用
- Cloud Functions のログを Firebase Logging で記録。出席判定の自動処理は結果を Firestore に保存し追跡可能にする。
- アプリはセマンティックバージョニングを採用。更新は App Store / Google Play を通じて配信する。

### 7.5 ユーザビリティ
- 初期リリースは日本語のみ対応。

### 7.6 データ保持・削除
- 出欠データは該当年度から 8 年保持し、その後削除する。
- 退学・卒業時に生徒アカウントにアクセスできず、関連データを削除できる機能を管理画面に設ける。
